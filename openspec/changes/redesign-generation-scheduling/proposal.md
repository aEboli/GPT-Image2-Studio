## Why

套图模式的调度边界分散在浏览器队列、每个 HTTP 请求的扇出助手和服务端会话槽位中。套图请求完成较快或收到暂时性 402 后，浏览器可能提前启动下一套；而每个 HTTP 请求各自计时，会让同时运行的套图把提交间隔压缩。配置区的并发数和提交间隔因此不能代表同一批实际发往上游的请求。

套图的同轮失败重排还会把暂时性容量错误立即重新送回拥堵窗口。自动补图又是新的请求 pass，若不保留条目已用尝试次数，就会把一次失败放大成多次上游请求。上游仍可能继续完成已经接受的请求，所以浏览器会出现“先显示 402，稍后又收到图片”的现象；这不是已接受任务被取消，而是本地调度提前结束了本轮等待。

部分中转站会在已经创建 Responses 任务后，以 HTTP 402 或带 `response.id` 的临时失败事件结束流。若本地把这种响应当成未创建任务并重新 POST，就会让同一条目同时拥有多个上游任务。带任务 ID 且明确属于临时容量/限流的失败 SHALL 进入原任务 GET 回查；明确认证、余额或配额失败，以及没有任务 ID 的失败，仍然直接报错。

## What Changes

- 将生成并发数量统一归一化为 `1`–`50`，默认 `20`；将提交间隔统一归一化为 `200`–`5000` 毫秒，默认 `1000`。两个值由浏览器请求、服务端扇出和会话限流共同使用。
- 新增按 `clientSessionId + generationScope` 共享的发车闸门，并把闸门放在五个并发扇出的真实上游生成调用之前。不同板块相互独立，同一板块的并发请求共用提交节奏。
- 让同一会话和板块的活跃任务槽位在首个请求进入时绑定并发上限；后续重叠请求不能用更大的前端值扩容当前活跃桶。
- 套图队列改为整套串行：当前套图的 SSE、自动补图和终态结算全部结束后，才允许下一套发起。入队时冻结同一批队列任务的调度参数快照。
- 套图生成、Logo 批量和套图补图关闭同轮即时重排。套图条目持久化上游尝试次数；自动补图最多为尚未达到两次尝试的条目再发起一次请求，并跳过已耗尽条目。用户明确发起的手动补图仍可执行。
- Responses 流或 HTTP 错误携带已创建任务 ID 且明确为临时容量/限流时，只回查原任务，不重复 POST；回查到完成结果时直接复用原图。
- 保留写真现有的失败重排语义，但写真生成与补图同样经过共享会话槽位和发车闸门。

## Non-Goals

- 不实现暂时性错误的退避重排；本轮套图自动路径通过关闭同轮重排和限制自动补图次数降载。
- 不实现“已预览但落盘失败”的字节级补救，也不改变现有落盘错误语义。
- 不新增每分钟压力推算 UI；配置控件只负责显示、持久化、快照和锁定。
- 不引入跨板块的全局闸门；套图与写真仍使用各自的 scope。
- 不把两次尝试上限扩展到写真或其他生成模式；手动补图不受该自动路径上限约束。
- 不改变没有已创建任务 ID 的上游单次请求内部重试、轮询或任务容量语义；只有带任务 ID 的临时失败会复用现有 GET 回查，避免重复 POST。

## Capabilities

### Modified Capabilities

- `runtime-configuration`: 调度参数范围、共享 slot、共享 launch gate 和生成期间锁定语义与实现一致。
- `creation-mode`: 套图队列串行化、调度参数快照和自动尝试次数上限。
- `portrait-mode`: 写真生成与补图使用同一会话/板块 slot 和 launch gate。

## Impact

- 调度原语：`lib/generation-launch-gate.mjs`、`lib/generation-task-slots.mjs`、`lib/limited-concurrency.mjs`。
- 服务端：`server.mjs` 五处并发扇出在真实上游调用前取得共享许可；套图生成和补图维护 `generationAttemptCount`；Responses 工作流对带任务 ID 的临时失败执行 GET-only 回查。
- 浏览器：`public/app.js`、`public/index.html` 传递并锁定调度值，队列模块维护严格串行和快照。
- 共享浏览器模块：通过 `scripts/sync-public-lib.mjs` 保持 `public/lib` 与 `lib` 一致。
- 测试：增加闸门、slot 绑定、队列串行、自动补图过滤、尝试次数持久化、Responses 临时 402 回查和服务端静态契约覆盖。
