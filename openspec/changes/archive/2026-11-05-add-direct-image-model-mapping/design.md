## Context

工作台已经拆分直连生图和文本/视觉配置。`lib/config-model-picker.mjs` 保存各通道独立的模型候选；`lib/image-route-config.mjs` 统一解析路由；`lib/responses-workflow.mjs` 按具体协议构造请求。已知模型 ID 同时参与图像能力、尺寸及高级参数校验，不能先把所有内部模型名直接覆盖成别名。

配置布局在宽屏使用两列，并对直连字段使用 `nth-child` 指定行号。本次已调整受新字段影响的位置规则，避免文本接口与映射重叠。当前工作树有大量已有改动，本次按用户批准的范围修改映射相关行，保留其他工作。

## Decisions

### 1. 明确单向规则

使用 `directImageModelMappings: [{ source, target }]`，默认空数组。两端去除首尾空白后按完整 ID 区分大小写精确匹配，最多替换一次，不链式替换、不自动互换、不模糊匹配。两端相同视为原样发送。重复 source 或单边未填写的规则在保存时提示修正；完全空白的草稿行不作为有效规则。

### 2. 两端可选也可填

左侧表示「当前模型」，右侧表示「请求模型」。共享当前直连生图接口的已获取模型候选，补充内置已知图像模型和当前已填写值；允许手动输入尚未出现在候选列表中的 ID。保留原有生图模型选择框；映射行不替代模型选择，也不自动选择新模型。

候选列表是辅助输入。提供方返回未知模型名称时不因名称格式而丢弃，也不把文本模型 ID 自动配置成规则。获取候选失败时显示原有错误并保留已填写内容。

### 3. 发送名称与能力判断分离

生图请求构造前解析原模型及其匹配规则，并保留能力判断所需的已知模型 ID：优先原模型的已知能力；原模型未知而明确映射目标已知时使用目标的能力。两者都未知时保持现有未知模型约束，不猜测能力。

仅在实际出站生图字段替换为 target：Images JSON/FormData 的 `model`、Chat Completions 生图的 `model`，以及 Responses 的 `image_generation` 工具模型。对于现有旧模型路径中与生图模型绑定的外层 `model`，保持既有协议语义并相应替换；独立配置的 Responses 文本模型不做映射。

映射也覆盖直连图像编辑、带参考图自动切到 edits、流式和非流式请求。其他通道与文本/视觉请求不读取该规则。记录应能区分所选名称与实际发送名称，避免界面或任务元数据把别名误当成其他模型。

### 4. 沿用配置与快照机制

新字段进入浏览器私有配置、保存合并、公共模型元数据、本地配置、JSON/FormData 私有请求解析及现有队列配置快照。省略字段保留已保存规则，显式空数组表示清空。排队任务使用入队规则快照，后续配置编辑不改变已排队请求。

规则归属于当前直连生图配置，随该配置保存；本次不增加按域名管理规则或自动跨 API 匹配能力。复用现有共享模块同步机制，禁止手工维护不同的 `lib` 与 `public/lib` 实现。

## Verification

- 规则解析：未匹配、单次匹配、大小写、空格、重复、清空、自映射和链式输入。
- 配置往返：浏览器、本地、请求覆盖、JSON/FormData、队列快照及凭据隔离。
- 请求模拟：Images 生成/编辑、Chat Completions 生图、Responses 图像工具与独立文本模型，分别覆盖流式开关与 2.6 能力。
- 界面：获取一次模型后两端候选更新；自定义和删除规则可保存恢复；新增区域顺序正确；宽窄布局不遮挡、不溢出。
- 维护：定向及相关回归测试、共享镜像同步检查、严格规格验证、差异和中文编码复查。真实付费生图不作为本地映射验证的前提。
