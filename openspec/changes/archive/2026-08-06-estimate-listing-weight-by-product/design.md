## Context

重量字段目前已经具备商品/包装证据分离、单位模式和估算标记，但缺证据时的本地实现仍固定返回包装 350 g、商品 250 g；同时 `applyCreationListingWeightFields` 无条件覆盖已解析字段。需要在不改变字段契约和导出接口的情况下修复估算边界。

## Goals / Non-Goals

**Goals:**

- 让无证据估算使用可复现的商品画像：品类、长度/结构、材质线索、数量和包装增量。
- 保留明确来源重量，并保留模型给出的有效 `Estimated:` 数值。
- 对图片/文字无法提供精确事实的场景继续使用保守估算并明确标记。

**Non-Goals:**

- 不从图片像素或标题臆造精确称重事实。
- 不修改 API 字段名、单位模式、导出模板或历史存储格式。
- 不把用户显式提供的重量改写为估算。

## Decisions

1. **证据优先，估算次之。** `getCreationListingWeightEvidence` 命中时继续生成 sourced 文本；无证据时先接受上游字段中带有可解析数值的 `Estimated:` 值，只有缺失/不可用才调用本地画像兜底。这样模型判断不会被固定值覆盖。
2. **共享商品画像。** 新增重量估算画像函数，复用来源文本中的品类、材质、长度和件数信号。轻薄中长服装（含旗袍/连衣裙）以约 320 g 商品净重为中心，包装增量约 100 g；其他既有品类保留不同基线并按数量、尺寸和材料做有限调整。
3. **确定性和范围。** 画像输出固定、可测试的克值并限制在合理上下界；单位转换沿用现有 metric/imperial/both 渲染。
4. **生成与历史读取一致。** `normalizeParsedListingDraft`、`makeMockCreationListingDraft` 和 `hydrateCreationListingDimensionsForRead` 统一使用同一个 fallback，避免新稿与历史稿再次分叉。

替代方案：完全依赖模型估算会在超时、mock 或历史回读时失去确定性；继续固定 350/250 则无法反映品类差异，因此不采用。

## Risks / Trade-offs

- [估算仍非实测] → 保留 `Estimated:`/`预估：` 前缀，并在 UI/导出中继续要求人工核对。
- [来源描述缺少品类词] → 使用通用中性基线，不声称精确；测试覆盖服装、电子、纸品和未知品类差异。
- [上游输出格式多样] → 只接受包含可解析重量数值的估算字段，无法解析时回退画像。

## Migration Plan

代码和测试发布后即可生效；历史记录仅在读取时非持久化补全，原始 JSON 不改写。回滚只需恢复重量估算函数和对应测试，不涉及数据迁移。
