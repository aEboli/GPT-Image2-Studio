## Why

2026-11-05 的批量 Listing 被用户怀疑同时提交多个请求、触发上游并发限制。检查当前浏览器、文本上游用量日志和代码后，当前证据不支持把这次慢归因于批内并发：批量控制器和服务端父 Listing 循环均逐条 await，模拟批量请求的峰值并发为 1；14:45 后完成的 8 次 deepseek-v4.1-flash 请求均成功，平均 144.48 秒。

更直接的瓶颈是提示资料冗余和推理开销。抽样套图的 Listing source 为 183,667 字符，effectivePlan 为 166,485 字符，占 90.6%；其中 slots 和 items 各 66,188 字符。近期请求输入为 77,708–93,298 token，使用 high 思考，推理 token 占输出 token 合计的约 88%。浮层耗时仅随事件更新，收到首包后长时间思考会看似一直停留在 2–3 秒。

仍存在独立的并发风险：不同套图的独立生成入口可并发，模拟 3 个入口峰值为 3；服务端 /api/creation/listings 无跨页面排队或同套请求去重；失败后批量循环立即进入下一条，无共享限流冷却。现有 Listing 文本进度也未持久化为可追溯日志。详细证据与边界见 design.md。

## What Changes

- 为模型构建精简的 Listing 专用输入，保留商品事实、SKU 数量与变体、尺寸重量、语言单位、禁用词及必要图片证据，排除整份画图计划和重复字段；本地归一化与内容校验继续使用完整来源。
- 所有 Listing 生成入口通过同一服务进程内的共享队列，默认上游活动请求上限为 3；同套图、同配置的活动请求合并等待。
- 区分明确的临时限流、账号额度/认证问题、普通单条失败和状态未知的中断；明确临时拒绝按 Retry-After 或短暂退避等待，不立即消耗后续整批；保持每条 Listing 最多 2 次上游 POST 的总预算。
- 显示批次总数、当前项、成功/失败/剩余、实际耗时及排队/思考/接收/冷却状态，并保留可追溯且不含密钥或完整提示词的诊断事件。
- 第一阶段保留用户当前思考等级。降低 high 的效果另行使用相同商品比较质量与时延，不擅自改变全局偏好。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- creation-listing-agent：Listing 专用输入投影、共享有界并发调度、限流与请求预算。
- creation-mode：批量 Listing 的状态、错误隔离和可追溯进度。

## Impact

- 实现涉及 Listing 专用输入、服务端调度与错误分类、客户端三工作者、文本进度和脱敏日志模块，以及对应回归与 public/lib 同步副本。
- 用户已确认实施并明确要求并发 3。实现保留原思考等级，单条全部兼容/修复/限流重试共享两次 POST 预算。
- 进程内 Listing 队列不能约束其他应用或其他服务进程，也不能单独保证整个上游账号的总并发。未进行真实上游费用请求对比，不承诺具体提速倍数。
