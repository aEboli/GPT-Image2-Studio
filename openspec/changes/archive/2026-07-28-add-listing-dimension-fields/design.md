## Context

Creation 记录已经保存通用 `dimensionSpecs`、单位模式、产品描述和参考说明。`dimensionSpecs` 可能是长度，也可能只有重量、容量或其他规格；包装尺寸则通常没有独立来源。Listing Agent 使用严格 JSON Schema，且本地服务和 Worker 共用生成模块，因此尺寸必须进入共享结构而不是只在页面上拼接文案。

## Goals / Non-Goals

**Goals:**

- 每个新生成 Listing 都包含非空的包装尺寸和产品尺寸双语字段。
- 对应来源明确时保留真实尺寸；没有对应来源时给出带显式标记的数值预估。
- 在页面、整条复制和导出中把两个尺寸字段固定放在最末尾。
- 保持历史草稿可读，并保持所有平台与运行时使用同一字段契约。

**Non-Goals:**

- 不新增商品表单输入项或尺寸编辑器。
- 不把图片像素分辨率当成商品或包装物理尺寸。
- 不自动发布 Listing，也不宣称预估尺寸是测量值。

## Decisions

### Decision 1: 使用两个双语标量字段

结构化响应增加 `packageDimensions` 和 `productDimensions`，`zhDisplay` 使用同名字符串字段。标量便于单字段复制、旧式整条复制和 JSON 导出，不引入额外嵌套结构。现有七个内容字段顺序保持不变，新字段只追加到末尾。

### Decision 2: 预估状态写入字段值

当来源没有对应证据时，英文值必须以 `Estimated:` 开头，中文值必须以 `预估：` 开头，后面给出包含物理长度单位的数值。这样单独复制字段或导出后仍能看到置信边界，不依赖额外 UI 徽标或未随字段复制的元数据。

### Decision 3: 产品与包装证据分开判断

产品尺寸可来自明确的产品尺寸字段或含物理长度单位的 `dimensionSpecs`。包装尺寸只接受明确标注为包装、装箱、彩盒或外箱尺寸的来源；普通产品尺寸不能复用为包装尺寸。模型可根据产品类别、可见结构和已知产品尺寸估算缺失项，但必须使用预估标记。

### Decision 4: 接受边界验证而不添加第二次改写

严格 Schema 要求两个字段及其中文对应值。归一化后还要确认四个值非空并含数值长度单位；缺少对应来源证据时检查预估前缀。继续沿用当前 Platform V1 单次上游请求和显式失败语义，不新增验证重试或静默确定性替代稿。

## Risks / Trade-offs

- 基于图片或类别的尺寸只能是估算，因此必须始终保留显式标记；最终发布前仍应由人工核对。
- 历史草稿缺少字段时只能显示为空值；重新生成后才会写入完整尺寸。
- 来源文本可能混合重量、容量和长度，提示和接受边界只把带物理长度单位的内容视为尺寸。

## Migration Plan

1. 增加结构、提示、预估边界、视图顺序、复制和导出失败回归。
2. 实现共享生成与规范化逻辑，并同步浏览器镜像。
3. 运行聚焦测试、全量测试、构建和严格 OpenSpec 验证。
4. 归档变更，将增量规格合并回主规格。
