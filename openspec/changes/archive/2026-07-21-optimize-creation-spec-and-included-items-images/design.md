## Context

`spec-table` 与 `accessory-gift` 是稳定的套图角色。当前规划器对所有尺寸角色共用同一段强制展示全部数值的提示词，而多个平台又把 `spec-table` 和 `in-box` 映射为固定构图。平台原生槽位会跳过部分通用角色意图，因此只修改一处文案不足以覆盖通用规划和各平台规划。

本次修改必须保留当前工作树中已有的 Listing、SKU 与界面改动，并且不能改变完整规格数据的持久化结果。

## Goals / Non-Goals

**Goals:**

- 让参数规格图解释少量关键规格如何帮助购买判断，而不是复刻数据库表格。
- 让到手清单图清楚展示实际收到的商品与配件，而不是默认模拟纸盒内部陈列。
- 对通用规划和平台原生规划使用一致、可测试的构图约束。
- 保留事实边界、数量完整性、单位模式和历史记录兼容性。

**Non-Goals:**

- 新增规格编辑器、包装开关或逐图版式控件。
- 改变 `spec-table`、`accessory-gift`、`in-box` 等稳定 ID。
- 从图片中生成新的规格、配件、数量或包装事实。
- 修改尺寸识别、单位换算或套图图片数量规则。

## Decisions

### 1. 完整事实与画面事实分离

计划顶层继续保存所有经过归一化的 `dimensionSpecs`，`size-capacity-fit` 继续获得完整尺寸核验信息。`spec-table` 的画面提示只从现有规格行中按属性去重并取最多 4 项，因此不会因同一参考说明中出现多组未解释的长度或宽度而生成重复表格行。

选择在提示词装配阶段做选择，而不删除顶层数据，是为了保留记录、重试和其他尺寸角色的事实完整性。

### 2. 参数规格图采用商品主导的注释结构

`spec-table` 保留事实型角色，但构图改为商品主体加尺寸线、局部标注或少量信息块。提示词明确禁止整页表格、电子表格、数据库清单和重复属性填充。每个可见数值仍受精确数值与单位锁约束。

### 3. 到手清单采用拆包平铺

`accessory-gift` 和平台 `in-box` 槽位必须把主商品、配件、赠品与确认的包装内容拆开并完整展示。普通背景应是干净的棚拍平面，而不是纸箱内部。包装只有在证据明确时才作为独立次要项；即便包含收纳包或包装盒，默认也展示在内容物旁边，而不是用它遮挡或容纳全部物品。

### 4. 通用与平台原生约束双层覆盖

通用角色的 brief、shopper question、role intent 和 rendering constraint 负责旧式/通用规划；平台图片类型的 `composition` 值负责平台原生规划。两层都使用同一视觉语义，避免某个平台因跳过通用 role intent 而回退到旧版纸盒或纯表格构图。

## Risks / Trade-offs

- [关键规格选择过少] -> 只限制 `spec-table` 画面，完整规格仍保留且尺寸适配图仍可展示；最多 4 个不同属性足以形成可扫描的决策信息。
- [复杂套装清单无法一屏完整展示] -> 继续保留完整库存锁，允许分组、网格和较小单品缩略图，但所有物品必须在包装外且数量可读。
- [包装本身就是商品或重要配件] -> 仅禁止无依据的包装舞台；有明确证据的包装、收纳包或礼盒可以作为独立清单项展示。
- [历史生成结果变化] -> 历史记录使用冻结提示词不重写，只有新规划或显式重新规划采用新构图。

## Verification

- Planner 回归测试分别覆盖重复规格的关键值选择、商品主导构图、禁止纯数据表、拆包平铺、包装证据边界和完整清单保留。
- Policy 测试锁定新的 `spec-table` 与 `in-box` composition。
- 运行专项测试、完整 `npm test`、public/lib 同步检查、Pages 构建和 OpenSpec strict validation。
