## Context

平台 resolver 先构造规范化 `slots`，再通过 `applySetOverrides()` 处理套图数量。当前实现对数组执行 `slice(0, imageCount)`，因此后续 `effectivePlan.slots` 与浏览器兼容类型选择器都只能看到被截断后的前 N 项。resolver 本身已经区分完整可编辑槽位 `slots` 与启用生成项 `items`，并支持通过 item override 重新启用已禁用槽位，因此无需增加新的目录或前端状态。

## Goals / Non-Goals

**Goals:**

- 通用电商在任意 0 至 18 的套图数量下持续暴露 18 个兼容图片类型。
- 套图数量仍决定默认启用和实际生成项数量。
- 保留现有逐槽启停、计划预览、冻结、队列和生成语义。
- 保持命名平台自身槽位上限以及 SKU/信息图重构的独立计数。

**Non-Goals:**

- 不为命名平台补齐到 18 项。
- 不增加图片类型、排序、提示词或逐图高级编辑入口。
- 不改变平台策略、图片类型定义、角色定义或历史冻结计划。
- 不自动替用户选择应当替换的图片类型。

## Decisions

### 1. 数量覆盖禁用尾部槽位而不截断目录

`applySetOverrides()` 继续按平台 profile 和当前可用槽位计算有效数量，但保留整个槽位数组。索引小于有效数量的槽位保持默认启用，后续槽位标记为 `enabled: false`。

选择该方案是因为 resolver 已把 `slots` 定义为可编辑槽位集合，把 `items` 定义为启用项集合。修复可以复用现有模型和浏览器渲染，不需要在前端复制平台目录。

### 2. Item override 在数量默认值之后应用

现有处理顺序保持不变：套图数量先建立默认启用范围，逐槽 override 再应用。用户先禁用一个默认项、再启用一个范围外项目时，最终启用数量不变，`items` 立即反映替换结果。

### 3. 计数与生成只读取启用项

`carouselImageCount`、兼容区域分子、`effectivePlan.items` 和实际生成继续从 `enabled !== false` 的槽位计算。兼容区域分母读取完整 `slots.length`；追加 SKU 与信息图重构只进入各自计数和生成项。

### 4. 平台目录边界保持不变

完整目录是“当前平台解析后仍可用的规范化槽位”，不是全局 18 项。通用电商 profile 有 18 项，因此始终显示 18 项；Amazon 等命名平台只显示自己的槽位，证据不足被安全省略的类型也不会被重新发明或用通用类型补齐。

## Risks / Trade-offs

- [冻结计划体积略增] -> 最多保留当前平台的 18 个轻量槽位，生成项与图片请求数量不变。
- [用户直接启用额外类型会增加张数] -> 保留现有逐槽启停语义；用户按界面既有方式先取消再选择即可完成等量替换，摘要始终显示实际启用数。
- [命名平台误显示 18 个通用类型] -> resolver 只保留当前 profile 已解析槽位，并增加命名平台上限回归。
- [禁用槽位进入实际生成] -> 定向断言 `slots.length`、`items.length`、`carouselImageCount` 和生成角色集合。

## Verification

1. 失败回归证明通用电商 `imageCount=5` 时应有 18 个 `slots`、5 个启用 `items`，当前实现会因截断而失败。
2. 修复后验证 `imageCount=0`、`5`、`18`，以及取消一个默认槽位并启用第 18 个槽位的替换流程。
3. 验证命名平台仍受自身规范化槽位上限约束，SKU 与信息图重构不进入兼容目录。
4. 运行定向测试、串行完整测试、public-lib 同步检查、Pages 构建和 OpenSpec strict validation。
5. 启动本地应用，在通用电商 5 张状态检查 `5 / 18` 与 18 个可见复选项。
