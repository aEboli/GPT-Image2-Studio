# 设计：批量 AI 营销提示词规划与自动入队

## 1. 用户界面

在现有三项开关附近增加一个批量入口。入口的可见性和可操作性由 AI 营销提示词开关控制：未勾选时不显示批量配置；勾选后显示“很多套 AI 提示词”按钮或折叠框。

展开后提供：

1. `方案数量`：整数，默认 1，建议范围 1–20。
2. `每个方案生成套数`：整数，默认 1，建议范围 1–20。
3. 批量进度区：显示当前方案、目标队列总数、已入队数量、重试次数和暂停原因。
4. 批量控制：开始批量、暂停后继续、取消剩余方案。已加入队列的方案不受取消剩余操作影响。

单套模式保持原有按钮和交互。批量模式启动后，当前表单输入、参考图文件、分析结果和模型配置会在批量快照中固定；用户修改表单不会改变已入队方案。

## 2. 批量状态模型

批量状态使用独立的 `batchId` 和方案条目列表，不把多个方案拼成一个 Creation set。每个条目至少包含：

- `index`、`total`、`status`
- `variationSeed`
- `attempts`、`lastRetryReason`、`startedAt`、`updatedAt`
- `queueJobId`、`setId`
- `error` 和 `terminalReason`

状态转换为：

```text
queued -> planning -> validating -> enqueued -> generating -> completed
                    \-> retrying -> planning
                    \-> paused
queued -> canceled
```

`enqueued` 只在 `createCreationQueueJob` 成功后写入。方案规划请求成功但入队失败时，条目进入暂停态，不重新发送同一份规划请求，避免重复规划和重复提交。

## 3. 执行顺序与队列边界

批量规划控制器只负责文本规划、校验和提交。每个方案的执行顺序如下：

1. 从批量快照构造当前方案的规划请求。
2. 调用现有 `/api/creation/plan` 流式接口。
3. 复用当前营销计划的事实、参考图、质量和局部修复校验。
4. 将通过校验的冻结计划放入所属方案的独立快照。
5. 构造该方案独立的 `FormData` 和 `queuedSet`，调用现有队列入队函数。
6. 标记当前方案已入队后释放所属执行槽位，立即领取下一个未开始方案。

方案入队后，现有套图生成调度器可以立刻消费队列；批量规划控制器不等待图片生成完成。按用户 2026-10-31 的明确要求，规划最多两个方案同时执行，套图最多两套同时生成；全局图片请求上限和间隔继续生效。后续双并发增量规范取代本提案原有的串行执行约束。

每个方案必须携带独立 `variationSeed`。每个队列任务都必须保留独立的队列快照。

## 4. 重试和超时

重试分为三层：

1. **单次文本模型调用**：保留现有结构化输出兼容重试和 JSON 修复重试。
2. **批量方案规划请求**：新增有界的瞬时错误和超时重试，建议默认最多 2 次，采用递增等待，例如 5 秒、15 秒。每次重试更新当前方案状态，不创建新的队列任务。
3. **图片生成**：继续使用现有套图单项重排、原任务回查、自动补图和账号级停止规则。批量层不重复实现图片重试。

以下错误直接暂停批量，不自动重复：API Key/权限错误、额度或账单错误、用户取消、输入校验错误、参考图无效、冻结计划与当前输入指纹不一致，以及模型明确返回不可恢复的协议错误。

模型超时需要区分“请求未建立”和“上游可能已经创建任务”。如果现有文本模型工作流无法确认原请求结果，批量层只允许在既有文本请求安全边界内重试；若无法确认是否已产生可计费任务，则记录为暂停并等待用户继续，不能盲目重复提交。

## 5. 暂停、继续与恢复

失败时尚未开始的条目保持 `queued`；已发出的另一个规划允许收尾，可用结果保存为暂停计划，不自动追加副本。用户点击“继续”时恢复暂停条目，并复用批量快照和已冻结结果；已入队条目不重新生成规划。

取消剩余方案只把尚未开始的条目标记为 `canceled`，不取消已经加入套图队列的任务。页面刷新后的恢复以浏览器会话内批量状态为主；如果本地持久化条件不足，至少通过队列 jobId/setId 去重，并明确提示未恢复的规划条目，而不静默重复提交。

## 6. 观测与安全

批量进度只展示方案级状态、尝试次数、等待阶段、错误摘要和队列 ID 的短标识。不得在批量状态或日志中写入 API Key、原始图片字节、完整敏感请求头或模型私密推理。

每个方案的 `requestTrace` 继续记录真实文本模型调用次数、重试原因和阶段耗时；批量状态额外记录批量序号，便于用户判断是第几套出现问题。

## 7. 验证策略

- 先增加纯函数测试，固定状态转换、输入指纹、重试计划和失败分类。
- 增加控制器测试，验证五套方案按序领取、最多两个同时执行、槽位独立补位，且每套使用独立变化种子。
- 增加失败测试，覆盖一次超时后成功、耗尽重试后暂停、账号级错误停止、取消剩余和继续执行。
- 增加前端源码/DOM 接线测试，验证 AI 开关关闭时批量入口隐藏，开启后可操作，批量进度能显示。
- 运行聚焦测试、公共库同步检查、OpenSpec 严格校验、`git diff --check` 和全量测试；真实模型调用与桌面视觉验收单独标记实测边界。
