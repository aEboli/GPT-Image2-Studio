## Context

当前 applyCreationMarketingPlan 先补齐受众/卖点关联事实，再将所有事实 referenceIndexes 与模型声明的 reference_indexes 取并集；buildCreationItemReferenceImages 对 marketingAssignment 直接映射这些编号。普通选图器的相关度与字节预算无法纠正 AI 分支的过度引用。普通分支也会持续选择有正分的同角色图，没有“本图所需视觉信息已覆盖”的停止条件。

当前全局最多上传 15 张，单项执行 6 MiB 字节保护；主规格与代码已取消固定八张上限。较早 active change adaptive-creation-reference-scheduling 的八张描述与当前实现存在历史差异。本提案以当前主规格和代码为基线，不回写或归档这些其他变更。

## Decisions

### 1. 先整套分工，再确定本图信息需求

复用 creative_brief 的 purpose、scene、action、framing、evidence_focus、new_information 描述逐图分工。计划必须先确认每图回答什么新问题、需要看清哪个部件/状态及其景别，再选择附件。

每图引用的受众/卖点/建议仍保留完整可追溯事实，但它们不自动触发相应图片加入。prompt 中只表达本图选定的事实和操作，不将全部分析照搬为画面文案。

### 2. 事实来源不等于图片附件

事实来源继续保存在 productInsights.confirmedFacts[].referenceIndexes。marketingAssignment.referenceIndexes 只表示最终实际附件；sourceIndexes 不因少发附件被删除或改写。

新规划可增加有版本边界的 reference_needs，逐项标识原始 index、用途（identity、detail、view、state、variant）、关联 fact_ids 和需要从图中读取的具体信息。它是候选需求，不能绕过服务端已核验事实、角色、款式、原始索引及字节预算。纯文字声明使用 fact_ids，无需虚构一种“必须附图”的用途。

选择流程：
1. 按现有锁定与款式匹配规则确定唯一主体，实际附件第 1 张为本款主体。
2. 从本图要呈现的外观细节、视角、可变状态、款式关系建立视觉需求。主体已经覆盖的需求直接满足，不再加图。
3. 按明确需求匹配候选，优先同时覆盖多个尚未覆盖需求的可靠原图；同一视觉证据的多个等效来源只需一个。
4. 每次加入必须带来新的必要信息；覆盖完成即停止，不能因为剩余空间足够继续填图。
5. 完全重复图片按内容身份识别；同名但内容不同的图继续独立；不能仅靠文件名或普通角色相同就删除一张独有视图。
6. 保留现有 6 MiB 字节预算和上游路线自身限制。若必要图片超预算，应给出可定位原因并进入已有有界局部修复/资料补充，不能悄悄丢失唯一必要细节。
7. 生成前冻结选中编号、逐图用途和最终提示词。附件标签与提示词按实际选中列表建立编号映射，避免提示词仍引用未发送的原图。

数量预期不是硬配额：

| 任务 | 常见附件 | 追加条件 |
| --- | --- | --- |
| 简单白底/完整商品展示 | 1 张本款主体 | 主体看不清必须展示的结构时补清晰图 |
| 单部件微距 | 主体，必要时加 1 张该部件细节 | 主体已可辨认则仍 1 张，不带尺寸卡或其他部件 |
| 自然使用场景 | 主体，必要时加状态/结构依据 | 默认自行创作场景与动作，不照搬来源背景；只有真实结构关系需要补充才加 |
| 尺寸/规格 | 主体及必要的款式或测量对应证据 | 已核验文字参数保留数值/单位/条件，不把所有规格卡广播 |
| 多角度/多款式 | 覆盖实际视图或款式的最小必要集合 | 每张新增图必须补足不同视面或对应款式，可能超过 3 张甚至 8 张 |
| CG/功能渲染 | 主体及确需的材质/状态证据 | 核验后的功能文字可直接作依据，避免把营销海报当作渲染底图 |

无 reference_needs 的本地计划从 contentAssignment、角色和已核验事实生成同等需求。不能把所有 coverageSources 直接标为必选。

### 3. 操作去重不依赖卖点措辞

对 use-scene 等真实操作图，在现有动作组基础上核对实际操作、使用关系和构图：
- 同一握车把动作、同一手部近景，换摩托/电动车或换保暖/按钮/防滑标题仍属高重复。
- 同一手机点按操作，换消息/地图标题不自动成为新的独立任务。
- 同一部件的微距证据与完整使用场景可以并存；白底商品与有真实配件清单的到手图可以并存。
- 一个新动作或清楚不同的证据关系可形成独立图，不能强制所有任务必须不同背景。
- CG 和功能渲染同时存在时，必须区分材质体积与功能作用，不允许一张黑底热流、一张相同姿态白底热流。

复用最多两轮的局部修复预算，只修冲突项，不移动已确认任务或覆盖锁定提示词。对操作、使用关系和取景共同确认的高置信重复，修复耗尽后保留任务及待调整原因，不自动发起该项生图、重试或补图；合格项继续生成，可生成与待调整数量同步到预览、队列和保存。仅有语义相似疑点的普通建议仍为警告，不扩大为整套失败。不能靠静默删图或无限修复伪造成功。

### 4. 白底重构渲染与商品主图分开

商业 CG 和功能效果渲染默认纯白背景（RGB 255/255/255），用符合真实材质的布光、轻微接触阴影和主体体积建立商业质感。暖色仅用于有事实依据的局部功能效果，不能让整体背景变成黑、橙或深色舞台。

用户批准时明确补充“需要添加光效效果”。因此白底不意味着去除效果：确认功能时使用有据的光效、体积热流或空间作用；没有功能依据时使用材质布光、反射及局部光效，不编造性能。

参考图提供商品身份，不能锁定整张源图画布。提示词明确重新安排支持的姿态、完整可售单位的组合、相机和留白；例如手套可从来源的并排平铺改为有轻微角度差的完整一双，或在结构允许时表现弯指/握持。不能为了变化补造不可见背面、内部构造、错误掌背部件或没有依据的翻盖状态。动作变化不强制真人、模特或无关道具。

严格白底商品展示使用独立 clean-catalog-main 约束：仅实际售卖物品、完整可售单位、纯白背景，无新增文案、功能热流、图标或额外道具。品牌商品自身实体标记保持来源。带光效的白底辅助图不等同严格商品主图。

Amazon 最终规则和类目例外需要以上传时适用规则核对。此次公共帮助页抓取未取得可读完整正文，因此本提案不声称 AI 渲染自动符合 Amazon 主图政策，不新增“已合规”标记或虚构通过平台审核。

用户明确的手动提示词/背景选择和平台硬约束优先；发现与默认方向冲突时在新规划提示中说明，不重写用户锁定内容。

### 5. 冻结、修复与历史兼容

- 新营销计划升级契约版本；相同输入和规划版本复用，版本变化时仅使当前新草稿缓存失效。
- 实现将营销计划版本升至 6、新草稿指纹契约升至 7。提交旧版 v0.2.116 已冻结队列时，继续按其原契约 6 核验指纹，而非绕过来源或输入变更校验；此路径已做生成和补图 HTTP 回归。
- 已预览的新计划冻结最终提示词、实际附件、用途与审核结果；生成、重试、队列和补图不重新选图。
- 无新元数据的历史冻结计划沿用既有原始提示词和附件，不能在补图时突然减少其输入。用户主动重新规划后才采用新策略。
- 实际选择保存于逐图 referenceSelection（version、referenceIndexes、needs），并与 marketingAssignment.referenceIndexes 保持一致。事实全量来源仍保存在 productInsights，原 coverage 元数据继续用于溯源；未选中的图不作为实际附件或源画布模板。
- SKU 始终以该 SKU 自身来源为准，多款对比保留逐款绑定；信息图重构继续严格单一来源。
- 不增加逐图规划请求、视觉相似度外部服务或隐式真实生图调用。

## Verification Strategy

先把 verification.md 三个反例转为失败回归，再覆盖替代来源/唯一细节/相同文件名/完全重复内容、多视面/多款分组、无图文字事实和预算不足。对生成、预览、冻结、保存、重试、补图验证相同附件与提示词，并覆盖历史兼容。为重复审核增加“不同卖点相同握把”和“同一动作不同微距证据不误伤”的正反例。为 AI 与规则图、无分析回退和界面预览说明验证白底/重构约束一致。

实现后运行聚焦 Creation 测试、全量 npm test、公共模块同步检查、发布事实检查、页面构建、严格 OpenSpec 校验和 git diff --check。当前 package.json 未提供 build:pages 脚本，实施验证时先核对真实构建入口，不能将不存在的命令报告为通过。真实模型出图属于额外的图像质量验收，单元测试只能证明规划/请求契约，不能证明图像像素质量或平台审核结果。
