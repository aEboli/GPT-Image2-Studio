## 现有链路

分析师：准备参考图 → `/api/creation/reference/analyze` → `requestPromptAgentAnalysis` → `requestStreamingText` → `text_progress` → 安全草稿 → 完整校验与应用。

营销：有效分析与商品资料 → 单次整套请求 → 结构化摘要 → 本地校验 → 必要时最多两轮局部修复 → 冻结提示词。界面变快不代表模型总时长已经降低。

## 优先方案

先以真实请求 ID 测量，再按有效分析复用、重复内容减少和修复上下文去重逐项对比。每次记录相同输入、同模型、同思考等级、实际 POST 数、输出 token、首段回答及总耗时，并核对事实覆盖和 20 图有效数量。令上游紧凑输出 JSON 可减少格式开销，但不能保证模型遵守，必须通过响应实际体量验证。

## 边界与取舍

不能把供应商日志的首字时间等同于浏览器拿到首段回答时间。网关缓冲时需要如实显示，前端无法恢复上游未转发的增量。不能从高 token 数推断内部推理内容或多次调用归属。

暂不采用多请求并行拆分：这会改变一次统筹的契约、增加调用、限流与重复分工风险；只有实测证据表明必要时才另行确认。不能为了速度自动降低 High 或删减证据、功能表现与参考约束。

## 已采用的实现

- 一次逻辑操作共享 requestId，每次真实 POST 使用不同 callId，记录真实 attempt。兼容重试和 JSON 修复仍共享原有两次 POST 预算；局部质量修复单独记录轮次。
- 只记录响应头耗时、首个正文块、首段回答、末段回答、接收区间、总计与供应商实际提供的输入/输出 token 数。首包可以只是心跳，不能据此推进回答接收。没有 token 数据时不推算。
- 分析师 API 的响应头通过 writeHead 一次性写入时，getHeader 未必可读。进度转发改为优先依据已经协商的 SSE 状态，避免合法 text_progress 事件被全部过滤。真实本地 HTTP 测试在上游仍阻塞最终响应时读取到首段回答。
- 严格结构化模式只在专用参数中发送 schema；已触发结构化兼容回退、严格 JSON 修复或原生 Gemini 仅支持 JSON MIME 时，仍发送内联完整 schema。没有 schema 参数时不得删掉唯一结构约束。
- 合格普通图片在修复上下文中仅发送 ID、营销目标、creative_brief 与事实引用，完整 prompt 留在服务器最终计划中；用户锁定项继续保留原文，问题条目的原始完整内容继续发送。已有有效分析仍只输出 suite_strategy 和 items。
- 分析与营销采用紧凑 JSON 和短摘要的指令，完整生成提示词、事实和数值条件不设硬长度限制。没有截断或重写既有冻结计划。

## 验证边界

固定 20 图夹具测得请求体缩小、调用数不变、最终提示词哈希一致。没有调用真实付费模型，不将夹具响应时长或请求体缩小比例冒充真实总耗时或输出 token 降幅。
