## Context

`lib/prompt-agent.mjs` 定义智能识别提示词及 JSON schema；`lib/creation-planner.mjs` 规范化结果并组装套图；`lib/creation-reference-labels.mjs` 选择每张图实际发送的参考；`server.mjs` 处理预览、生成和补图；`public/app.js` 管理识别应用、冻结计划与展示。

现有 `creation-item-requirements.mjs` 把任意颜色关键词或一个 SKU 当成多款依据，且只拦截 `spec-table`。服务端已有的过滤代码误放在写真处理器；套图生成及冻结计划仍可绕过。现有识别应用会删除 `roleLocked`，覆盖人工指定的参考主体。

## Decisions

### 同一次识别完成商品分析

扩展现有视觉请求的职责和结构化输出，不创建独立多代理系统，不新增第二次分析请求。分析内容使用 `product_insights`，前后端规范化为 `productInsights`。

分析包含：`appearanceLocks`、`confirmedFacts`、`sellingPoints`、`painPoints`、`usageScenarios`、`unknowns`、`conflicts`。事实有稳定 id 和 `referenceIndexes`；买点和场景通过 `factIds` 绑定事实。无法找到来源或引用失效的项目不进入可上图事实。使用场景属于创意推断，只指导环境与动作。

### 主体与文字证据的优先级

人工指定主主体 > 单一商品主体 > 可读辅助资料。用户主主体的结构与颜色决定输出商品。分析记录掌心/手背、翻盖/开口、控制器位置、缝线、数量等外观锁定点；证据冲突时保留主主体外观，把冲突显示为待确认，不把冲突文案塞进各张提示词。

### 拦截是服务端约束

复用现有 `evidenceBlocked` 和 `evidenceRequirement`，覆盖尺寸图与多 SKU 项。生成前重新计算，不信任冻结计划的布尔标记；补图也重新计算。被拦截项保留卡片并标记跳过，不排队、不重试、不占并发，也不上传只被它使用的参考图。

多 SKU 数与完整可售单位数分开：一双左右手套是一个 SKU；同一 SKU 的不同视角合为一组；一个复合颜色标签如“brown black silver”仍是一个变体。结构化 SKU 资料优先于模糊描述，只有明确列出多种可售选项的资料才允许文本变体清单。

### 场景分配先于提示词

先为整套图建立场景任务，再逐项组装。每项记录场景 id、环境、动作、证据 id 和人物方式，避免每张独立抽取背景造成重复。商品主视觉、细节和多角度保持各自任务；生活场景默认无人物或只露手，必要穿戴图再使用局部身体。泛化到商品类型，不针对手套硬编码所有默认场景。

### 旧数据兼容

旧记录不迁移、不重写。没有 `productInsights` 时继续使用已有事实与类目场景，生成前仍执行缺数据约束。信息图重构是独立已有分支，不把普通商品参数图规则误用于原图版式重构；商品主体不被重构源图替换。

## Risks

- 提示词约束只能降低生成漂移，无法保证逐像素一致；最终仍需真实图片抽样验收。
- 图片里可读数字可能来自错误素材。冲突数字必须提示，不能擅自挑选或合并。
- 严格拦截会减少实际生成张数；界面须显示“可生成/已跳过”，不能虚报满额完成。
- 序列化、历史复用或参考图变化容易留下旧分析。分析只在来源仍匹配时应用；失效后保留展示但不用于新计划。
