## Context

`release:patch` 当前在内存中生成新内容后，通过一个 `Promise.all` 直接覆盖包文件、页面、文档并新建发行说明。任一写入失败不会撤销已经成功的并行写入。同时，维护文件使用无边界 `replaceAll` 更新旧版本字符串，因此当前版本事实之外的历史文本也会被修改。`check:release` 虽然要求正则只匹配一次，却在原始 HTML 文本上工作，注释中的完整标签能够满足检查，格式不同的第二个 `.app-version` 元素也可能被忽略。

Prompt Agent 的普通图片反推、参考图编排和其他参考分析共用历史存储。请求阶段已有模式，但历史归一化会丢弃该事实；浏览器随后把全部带可复用文本的历史传给模板合并函数。参考图编排的 `prompts[]` 因此会被取第一条并错误映射成一个普通自动模板。

`application-versioning` 已要求工作台只显示一个可见版本标签。本变更修改的是发行工具如何证明该要求，不新增版本展示能力，所以版本 DOM 的增量契约归入 `project-maintenance`。

## Goals / Non-Goals

**Goals:**

- 补丁更新在可处理的文件系统失败后呈现全成或全不成的结果。
- 只修改每个文件中定义明确且唯一的当前版本事实，保持其他文本逐字不变。
- 发行检查只接受一个真实、可渲染且与包版本一致的工作台版本元素。
- 新历史保留分析模式，Prompt Kit 只导入普通图片反推，并兼容可可靠识别的旧普通反推记录。
- 为审查中的每个反例建立直接自动化回归证据。

**Non-Goals:**

- 不创建通用数据库事务或通用 HTML 处理框架。
- 不自动提交、打标签、构建安装包或发布外部制品。
- 不迁移、删除或重写既有 Prompt Agent 历史文件。
- 不把参考图编排的多条提示词压缩、拆分或转换为 Prompt Kit 模板。
- 不把某次发布说明中的测试数量提升为长期产品契约。

## Decisions

### 1. 用文件专属锚点生成完整更新计划

补丁命令先读取所有来源并在内存中生成更新计划。`package.json` 与锁文件继续通过结构化 JSON 字段更新；README、Windows 文档和工作台页面分别使用与发行检查相同的当前版本事实定位规则。每个适配器必须证明旧事实恰好出现一次，并在生成结果中证明新事实恰好出现一次。零匹配、多匹配、旧事实不一致或目标发行说明已存在时，命令在任何受维护文件改变前失败。

适配器只替换匹配锚点中的版本值。示例、迁移记录、旧标签命令，以及 `1.2.30` 这类仅包含 `1.2.3` 字符串的历史文本保持原字节内容。采用文件专属适配器而不是全局单词边界，是因为各文件的当前事实格式不同，且语义锚点比数字边界更可靠。

### 2. 暂存整组输出并在失败时回滚

所有目标内容验证完成后，命令在各目标同目录写入唯一临时文件；只有全部暂存成功才进入提交阶段。提交阶段为既有目标保留原始备份，逐个将暂存文件替换到正式路径，并记录已经处理的目标。若任何替换失败，则按逆序恢复每个既有目标的原始内容，删除已提交的新发行说明，并清理本次临时文件和备份。命令只有在整组提交完成后才报告新版本。

回归测试通过可控文件系统失败点覆盖“暂存前失败”和“部分提交后失败”，并比较所有既有文件的原始字节及发行说明是否存在。该边界处理命令执行期间返回的文件系统错误；进程被强制终止或底层存储同时阻止写入与回滚不在可保证范围内，但遗留的临时/备份文件不得被发行一致性检查当成当前事实。

临时文件或备份的清理错误不得被吞掉。暂存或回滚路径清理失败时，错误明确说明目标未完整提交以及尚未清理的事务状态；全部目标已经提交后若仅备份删除失败，命令保留新版本，不执行会破坏已提交结果的二次回滚，并明确报告“内容已提交但清理未完成”及待处理备份路径。

### 3. 版本检查识别实际版本元素而不是任意原始文本

工作台检查从非注释、非模板的 HTML 元素中识别 `app-version` class token，要求恰好一个候选。候选必须可渲染，不得带 `hidden` 或 `aria-hidden="true"`，其文本和无障碍版本值都必须与根包版本一致。注释内的标签不计数；页面中任何第二个 `.app-version` 元素都使检查失败，即使一个元素正确、另一个元素格式不同或版本陈旧。

发布补丁的页面适配器复用同一候选识别规则，避免“检查能识别的事实”和“更新会修改的事实”分叉。CSS 布局与最终视觉可见性继续由 `application-versioning` 的现有响应式测试和人工视口检查负责。

### 4. 历史记录保存规范化的分析模式

服务端在历史条目中保存一个明确的分析模式判别字段。普通图片反推使用稳定的 `image-to-prompt` 值；参考图编排、Creation 参考分析、Portrait 参考分析等保留各自现有模式值。存储归一化和历史 API 必须往返保留该字段，浏览器同步在提取模板文本之前先判断导入资格。

带明确判别字段的记录只有值为 `image-to-prompt` 时才有资格补齐模板；任何其他值或未知非空值均保留在历史视图中但不进入 Prompt Kit。即时保存普通反推结果与打开 Prompt Kit 后的长期历史补齐使用同一资格函数。

存储归一化只在来源记录原本包含模式字段时规范化其值。读取或追加新记录不得给缺少模式的旧记录合成空字符串字段，避免一次普通追加变成隐式历史迁移。

### 5. 缺少模式的旧记录采用窄结构兼容

既有历史没有分析模式，不能简单把空值解释为普通反推。兼容层只接受已由 `image-to-prompt` 能力定义的两类普通结果：严格的 `subject`、`framing`、`scene`、`visual`、`avoid` 五组结构，或同时具有非空 `prompt` 与可识别旧版反推字段的旧结构。只有 `prompts[]`、未知对象或普通/编排语义不明确的记录失败关闭，不创建模板。

兼容判断只影响是否自动补齐，不改变历史展示、原始 JSON、历史删除语义、已存在模板或本地屏蔽 ID。已经存在的同 ID 模板仍按现有规则原样保留。

## Risks / Trade-offs

- [多文件提交不具备操作系统级事务] -> 全量暂存、同目录替换、原始备份和逆序回滚把正常文件系统错误收敛为可测试的全成或全不成结果。
- [HTML 识别器范围过窄] -> 只实现静态工作台版本元素所需的 HTML 语义，并用注释、模板、属性顺序、class token、隐藏和重复元素反例验证；不以任意字符串搜索代替元素识别。
- [旧记录兼容减少导入数量] -> 资格判断失败关闭；用户仍可在历史中查看和复制记录，避免把语义不明的内容静默写进 Prompt Kit。
- [新增模式字段影响旧数据] -> 读取时保留缺失状态并使用结构兼容，不要求重写现有历史文件。

## Migration Plan

1. 先增加发行失败、锚点、DOM 和历史模式的失败测试。
2. 实现文件专属更新计划、暂存/回滚提交和共享版本元素识别。
3. 保存历史分析模式并在模板同步前执行普通图片反推资格判断，同步公共浏览器模块。
4. 运行定向及全量验证，以最终测试输出校正发布说明事实。
5. 合并增量规格并归档；回滚代码不会改变既有历史数据格式或内容。

## Open Questions

- 无。旧记录采用失败关闭的结构识别，非普通分析结果不自动转换为模板。
