## Context

套图模式目前有 16 个稳定的电商角色，参考图用途包括 `product`、`reference-product`、`package`、`material`、`dimensions`、`usage`、`scene`、`style` 和 `other`。现有规划会让部分非主体参考图覆盖到相应套图角色，但不会为每张非主体图生成独立重构结果。

用户希望上传混合参考图时，主体图继续锁定商品主体，非主体图作为“信息图”逐张重构。例如 8 张参考图中 3 张是主体、5 张是信息相关图片，则生成计划应在原有套图角色后追加 5 张信息图重构项。

## Goals / Non-Goals

**Goals:**

- 在套图模式增加默认开启的“信息图重构”开关。
- 将非主体参考图逐张追加为信息图重构项，且追加在 16 个套图角色和 SKU 补图之后。
- 每个重构项保留源信息图的原始信息、结构和信息层级，并用主体参考图中的商品作为新主体。
- 计划预览、正式生成、队列占位、manifest 记录和修复流程保持一致。

**Non-Goals:**

- 不改变现有 16 个套图角色的角色 ID、默认顺序或数量选项。
- 不新增独立页面或独立生成模式。
- 不把主体参考图当作信息图重构源。
- 不尝试自动翻译或改写原信息图里的参数、步骤、清单、尺寸或承诺。

## Decisions

1. **把信息图重构建模为追加 item，而不是第 17 个套图角色。**
   - Rationale: 现有 `imageCount` 和角色选择依赖 4/6/8/10/12/14/16 的固定套图角色。追加 item 可以保留原有角色体系，并让记录、修复和队列天然复用现有 item 流程。
   - Alternative considered: 将 `infographic-rebuild` 放入 16 个角色选择器。该方案会让用户误以为它占用套图数量，并破坏“每张非主体图生成一张”的需求。

2. **主体定义只包含 `product` 和 `reference-product`，信息图定义为其余参考图用途。**
   - Rationale: 现有参考图用途已经表达“主体”和“非主体”边界，复用它可以避免新增复杂分类 UI。
   - Alternative considered: 增加一个单独的“信息图”参考图类型。该方案会让尺寸、步骤、包装、场景等现有用途失去语义，不利于提示词保真。

3. **每个信息图重构项只附加主体参考图、对应的信息图源、风格参考图和可选 Logo。**
   - Rationale: 重构必须明确“当前这张信息图源是什么”，避免其他非主体参考图串入，导致信息混杂或新增未提供内容。
   - Alternative considered: 对每个重构项继续附加全量参考图。该方案更简单，但更容易让模型混淆多张信息图的内容。

4. **开关字段进入计划、生成、修复和 manifest。**
   - Rationale: 预览、正式生成和记录修复必须使用同一个计划形状；保存字段也方便记录页展示与后续补图复用。
   - Alternative considered: 只在前端临时追加预览项。该方案会让服务端正式生成和记录修复无法复现同一套计划。

## Risks / Trade-offs

- 模型可能改写源信息图文字或参数 -> 提示词明确要求保留原信息、不新增未提供数据，并把源信息图作为 visual/info blueprint。
- 非主体图过多会增加生成数量和耗时 -> 开关默认开启但可关闭，生成数量在预览和队列占位中可见。
- `style` 或 `other` 参考图可能不是信息图 -> 默认按用户定义“非主体图包括其他”处理，用户可关闭开关或将图片改为主体/移除。
- 历史 manifest 没有新字段 -> 归一化时默认 `infographicRebuildEnabled` 为 false 或依据已有 items 推断，不破坏旧记录。

## Migration Plan

- 新字段只在新生成的套图 manifest 中写入；旧记录通过归一化默认值兼容。
- 前端脚本和 `public/lib` 镜像保持同步，避免本地与静态部署行为分叉。
- 回滚时移除新增开关字段和 `infographic-rebuild` item 生成逻辑即可，旧 manifest 中的额外字段不会影响读取。
