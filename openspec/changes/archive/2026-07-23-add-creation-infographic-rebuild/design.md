## Context

套图模式目前有 16 个稳定的电商角色，参考图用途包括 `product`、`reference-product`、`package`、`material`、`dimensions`、`usage`、`scene` 和 `other`。已移除的独立 `style` 参考输入不属于信息图来源。信息图重构已经能为每张非主体图生成独立结果，但当前实现会同时传入主体参考图，并把商品、平台、语言、视觉风格、Logo 和受众转化上下文拼入提示词。

用户希望每个信息图重构项只处理它对应的源图。例如 8 张参考图中 3 张是主体、5 张是信息相关图片，计划仍追加 5 张重构项，但每项请求只能包含对应信息图一张，不能被其余 7 张图片或套图资料影响。

## Goals / Non-Goals

**Goals:**

- 保留默认关闭、可显式开启的“信息图重构”开关。
- 将非主体参考图逐张追加为信息图重构项，且追加在 16 个套图角色和 SKU 补图之后。
- 每个重构项把对应源信息图的原始上传文件作为唯一视觉与信息依据，保留原图商品、文字、数字、单位、参数、图标、颜色、版式、层级、相对位置和阅读顺序。
- 每个重构项排除所有主体参考图、其他信息图、Logo 和套图文案上下文；只沿用冻结的技术生成参数。
- 计划预览、正式生成、队列占位、manifest 记录和修复流程保持一致。

**Non-Goals:**

- 不改变现有 16 个套图角色的角色 ID、默认顺序或数量选项。
- 不新增独立页面或独立生成模式。
- 不把主体参考图当作信息图重构源。
- 不替换源图中的商品，不自动翻译、改写、增删或补全原信息图里的文字、参数、步骤、清单、尺寸或承诺。
- 不取消用户已经选择并冻结的模型、比例、尺寸、质量、格式或推理参数。

## Decisions

1. **把信息图重构建模为追加 item，而不是第 17 个套图角色。**
   - Rationale: 现有 `imageCount` 和角色选择依赖 4/6/8/10/12/14/16 的固定套图角色。追加 item 可以保留原有角色体系，并让记录、修复和队列天然复用现有 item 流程。
   - Alternative considered: 将 `infographic-rebuild` 放入 16 个角色选择器。该方案会让用户误以为它占用套图数量，并破坏“每张非主体图生成一张”的需求。

2. **主体定义只包含 `product` 和 `reference-product`，信息图定义为其余参考图用途。**
   - Rationale: 现有参考图用途已经表达“主体”和“非主体”边界，复用它可以避免新增复杂分类 UI。
   - Alternative considered: 增加一个单独的“信息图”参考图类型。该方案会让尺寸、步骤、包装、场景等现有用途失去语义，不利于提示词保真。

3. **每个信息图重构项只附加对应的信息图源一张。**
   - Rationale: 源信息图已经包含需要保留的商品与完整画面。主体参考图会诱导模型换商品，Logo 会改变画面，其他参考图会造成信息混杂，因此三者都必须排除。
   - 原始上传文件直接用于重构来源，不使用通用生成参考图的 1024 边长 JPEG 压缩副本，避免小字、数字、单位和参数在请求前损失。
   - Alternative considered: 附加主体参考图、当前源图和可选 Logo。实测反馈表明该方案会让结果变化过大，违背“原样重构”。

4. **信息图重构使用固定 source-only 提示词，并在运行时再次收敛。**
   - Rationale: 仅在规划阶段生成干净提示词不足以修复已有 manifest。正式生成和修复必须按 item role 使用同一固定提示词，排除商品资料、平台、类目、场景、视觉语言、目标语言、参考分析备注、受众策略和 `conversionIntent`。
   - Alternative considered: 继续执行冻结计划中的历史提示词。该方案会让旧记录修复时重新引入已知污染。
   - 冻结计划仍保存原 item prompt 和转化元数据以兼容记录，但生成与修复执行时，`infographic-rebuild` 的运行时 prompt 必须以 canonical prompt 覆盖历史值；这是通用“执行保存提示词”规则的显式例外。

5. **开关字段和技术生成参数进入计划、生成、修复和 manifest。**
   - Rationale: 预览、正式生成和记录修复必须使用同一个计划形状；保存字段也方便记录页展示与后续补图复用。
   - Alternative considered: 只在前端临时追加预览项。该方案会让服务端正式生成和记录修复无法复现同一套计划。

   模型、比例、尺寸、质量、格式和推理强度仍通过现有参数字段传入上游，不拼接为营销或重设计指令。若配置画布与源图比例不同，提示词要求只延展原有背景或留白，不裁切、拉伸、重排或重设计源内容。

## Risks / Trade-offs

- 模型可能改写源信息图文字或参数 -> 固定提示词要求逐项保留，并把唯一源图作为视觉与信息权威。
- 原始信息图文件会增加浏览器到 Local/Worker 的请求体积 -> 仅非主体重构来源绕过生成压缩，主体参考仍沿用现有压缩策略；超出部署请求限制时明确失败，不静默替换为降质副本。
- 非主体图过多会增加生成数量和耗时 -> 开关默认关闭并可显式开启，生成数量在预览和队列占位中可见。
- `style` 或 `other` 参考图可能不是信息图 -> 默认按用户定义“非主体图包括其他”处理，用户可关闭开关或将图片改为主体/移除。
- 历史 manifest 没有新字段 -> 归一化时默认 `infographicRebuildEnabled` 为 false 或依据已有 items 推断，不破坏旧记录。
- 历史 manifest 保存了受污染提示词 -> 生成与修复运行时按 `infographic-rebuild` role 重新使用固定 source-only 提示词，但继续保留原 item 的技术参数。
- 历史 manifest 不保存原始参考图字节 -> 修复前必须从复用流程重新上传匹配来源；缺少来源时 fail closed，不回退到其他图片。

## Migration Plan

- 新字段只在新生成的套图 manifest 中写入；旧记录通过归一化默认值兼容。
- 前端脚本和 `public/lib` 镜像保持同步，避免本地与静态部署行为分叉。
- 回滚时移除新增开关字段和 `infographic-rebuild` item 生成逻辑即可，旧 manifest 中的额外字段不会影响读取。
