## 设计

### 1. 优先精简输入

保留本地完整 source，新增仅供模型消费的明确字段投影；不要直接删除持久化 manifest 的 effectivePlan。从计划提取影响 Listing 的平台、品类、事实、数量、尺寸单位和已确认卖点；保留英文/德文/中文契约和未知信息边界。图片证据按 itemId 合并，完成图片优先，计划元数据仅补缺，不重复发送 imageItems、plannedItems 及整套 slots/items。

对抽样套图比较模型请求体长度，验收目标为 source 至少下降 70%。实际只读手套样本从 183,667 降为 22,853 字符，下降 87.56%；包含缩进的 Source JSON 从 257,558 降为 33,151 字符。脱敏真实结构 fixture 的 source 从 125,820 降为 14,912 字符，下降 88.15%。商品关键事实、尺寸轴、SKU 数量、颜色与禁用词由独立回归验证保留，自动测试不依赖用户磁盘记录。

浏览器生成请求只提交 setId、当前配置和 reasoningEffort；服务端当前已经以已保存 manifest 为来源，未使用 payload.set。删除冗余 set 之前核对所有入口契约与现有测试。

### 2. 在服务端守住三个 Listing 槽位

手动、自动、批量和不同页面请求汇入同一 Listing 调度器。服务进程内全局上限为 3，任务从真正准备调用上游到响应体读取完成均持有槽位。排队阶段不计入单次上游 600 秒截止时间。冷却期间不启动同队列后续项。

活动去重键包含 setId、影响 Listing 的来源指纹、端点/模型/思考等级与认证配置的不可逆指纹；不得在日志或响应中出现原始 Key。重复请求合并等待，只生成并保存一次。不同配置不能误复用。调用方断开时移除该等待者；无人等待的排队项取消，执行项按现有取消信号收尾；最后一个等待者离开前不得取消仍有消费者的任务。任务结束在 finally 释放槽位。

该队列仅管理 Listing。若后续有证据表明营销规划等文本任务抢占同账号额度，再单独讨论端点级共享文本调度，避免本次变成所有 AI 功能的调度重构。

### 3. 错误分类与请求预算

- 明确临时限流：保留上游 HTTP 状态、错误码、Retry-After；先排除认证/余额/额度耗尽。短暂冷却后可重试当前条一次，所有格式修复、参数兼容和限流重试合计最多 2 次 POST。可复用已有兼容机制，避免多层各自重试。
- Retry-After 表示整个 Listing 队列的下一次可提交时间；无有效提示时先采用 5 秒短暂退避。不早于有效 Retry-After 重试。要求等待超过 60 秒或连续 3 条明确临时限流仍未恢复时，停止提交并列明未开始项，保留已完成草稿，用户再次运行时只补缺失。
- 明确认证/额度耗尽：停止本批后续提交并显示真实原因，不把 429 全部当成临时限流。
- 普通单条失败：记录原因后继续下一条，保留现有隔离契约。
- 连接中断、超时、已有部分文本等状态未知：不自动重放可能已经执行的生成；提示用户检查或再次手动补缺。普通失败间隔保持轻量，不人为给所有成功任务增加几秒延迟。

### 4. 可观察性

批次状态由 batch 自身维护，单条 generate 的“正在生成”反馈不得覆盖总数。展示总数、成功/失败/活动/未开始数及实际经过时间；排队、等待首字/上游思考、回答接收、校验、冷却分开标识。只显示真实进度，不伪造百分比。

Listing 事件记录 batchId、setId、requestId、attempt、阶段、状态、排队/上游/总耗时、可用 token 统计与经过清理的错误。只记录元数据，避免每个 token 的完整累积文本进入持久化日志。保持已有图像日志展示与三语 Listing 保存、复制、导出契约。
